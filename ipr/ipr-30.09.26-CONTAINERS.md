## 2. Виртуализация (виртуальные машины)

### Плюсы
- У каждой VM своё изолированное окружение и своя ОС.
- В каждой VM свой набор софта, каким бы кривым он ни был.
- Сломал VM, остался в ней: побег из гипервизора (hypervisor escape) — редкость.
- Ресурсами можно гибко управлять.
- VM не влияют друг на друга (кроме конкуренции за общие ресурсы).
- Возможен overcommit / oversubscription (выдача ресурсов «с запасом», пока клиенты не начнут жаловаться).
- Горячая миграция между хостами без рестарта.
- Заморозка состояния, snapshots, лёгкий бэкап.
- Управление как IaC (Infrastructure as Code) через Terraform, Ansible.
- Большинство современных VPS/VDS — это виртуальные машины.

### Минусы
- Каждая VM потребляет ресурсы, даже когда ничего не делает.
- 100 VM с Ubuntu Server = 100 копий ядра в памяти и 100 копий одинаковых бинарников на диске.
- Каждой VM нужен админ: внутри нужно обновлять ОС, следить за уязвимостями сервисов (вопрос «как?»).
- Provisioning занимает минуты, перезапуск — десятки секунд (бывают исключения).
- Развернуть на VM нужное окружение долго, сложно и хрупко.
- Сменить версию ОС на уже готовом деплое практически невозможно.
- Разработчикам такой подход не нравится: вариант «у меня на машине работает, давай в продакшен» трудно осуществим.

## 3. Причины появления контейнеров

| Ситуация | Проблема |
|---|---|
| **Традиционный общий хостинг** | Много клиентов с разными требованиями; безопасность клиентского кода на самом низком уровне |
| **Собственная разработка и деплой** | Dependency hell (Node.js, Python, PHP); по три версии PostgreSQL, MongoDB и т.д.; всё лежит в `/home/<кто-то>/`; админ деплоит по полгода, а у разработчиков простые пароли и `sudo` |
| **Поставка готового кода заказчику** | У заказчика другая среда (Java от IBM, старый RedHat); инсталлятор и инструкция по установке ломаются, «что-то пошло не так» |
| **Масштабирование** | Нужно быстро и одинаково разворачивать множество копий |

## 4. Предшественники контейнеров

### chroot (chroot jails)
- Каждому пользователю выдаётся свой «корень» (например, `/mnt/user`), в который он запирается вызовом `chroot(2)` или командой `chroot(1)`.
- Появился в UNIX V7 / BSD 4.2, около 1980 г.
- **Ограничения:**
  - пространство процессов общее;
  - устройства общие;
  - сеть общая;
  - ресурсы не ограничены (кроме квоты на файловую систему);
  - из chroot можно сбежать, если получить root.
- Для работы внутри chroot все нужные библиотеки, бинарники и устройства должны лежать внутри него.
- Применяется в build toolchains, кросс-компиляции и на самых дешёвых тарифах shared hosting.

### FreeBSD jails
- Идея та же, но запирание делается через `jail(2)` / `jail(8)`.
- Появились во FreeBSD 4.0, 1999–2000 гг.
- **Что умеют:**
  - каждый jail изолирован в своём sandbox;
  - видит только свои процессы;
  - у каждого своя сетевая конфигурация (менять её нельзя);
  - взаимодействие между разными jail невозможно.
- **Минусы:** ресурсы не ограничивались (до FreeBSD 9.0, 2012), настройка сложная («шаманизм»).
- «Почти Docker, но совсем не Docker». Используется в узком кругу любителей *BSD.

## 5. Идея контейнера

Доводим до конца идею FreeBSD jails:
1. Создаём отдельные пространства **для всего** (PID, UID, IPC и т.д.).
2. Запускаем в них полностью изолированные процессы.
3. Ограничиваем процессы по ресурсам (память, CPU, диски).
4. Выдаём каждому пространству свой образ файловой системы.
5. Единственный общий элемент — **ядро Linux** (даже libc у каждого своя).

**Сравнение архитектур:**

```
Виртуальные машины          Контейнеры
------------------          ----------------
App   App                   App   App
ОС    ОС                    Docker
Гипервизор                  ОС
Железо                      Железо
```

Контейнеры не тащат за собой отдельную ОС для каждого приложения, поэтому легче и быстрее.

## 6. Три кита контейнеров в ядре Linux

### 6.1. Пространства имён (namespaces)
- Ключевая механика ядра Linux для **изоляции процессов**.
- В нужном объёме появились в ядре **3.8 (2013)**.
- Создаются через `unshare(2)` или `unshare(1)`.

**Полезные типы:**

| Тип | Что изолирует |
|---|---|
| **PID** | В каждом пространстве процессы нумеруются с 1 |
| **User** | Свои пользователи, свой root, свои права и ограничения |
| **Network** | Свои IP-адреса, маршруты, интерфейсы, имена хостов |
| **Mount** | Свои точки монтирования с разным уровнем изоляции |
| **cgroups** | Свои ограничения ресурсов в пределах namespace |

- С точки зрения изолированного процесса, он в системе один и больше никого нет.
- С точки зрения хоста это обычный процесс, запущенный в этом пространстве.

### 6.2. Группы управления (control groups, cgroups)
- Ключевая механика ядра для **ограничения ресурсов** группы процессов.
- Появились в 2008 г. (на слайде указано ядро 2.6.4).
- Создаются через `/sys/fs/cgroup` или `cgcreate(1)`.
- **Что умеют:**
  - ограничивать ресурсы: CPU, RAM, I/O, файловую систему;
  - вести учёт использования ресурсов;
  - управлять группой процессов (остановка, перезапуск и т.д.).
- Обычно на каждый namespace создаётся своя cgroup.
- **OOM-killer** знает про cgroups и «приходит» к процессам, съевшим свой лимит памяти.

> Примечание: в реальности cgroups появились в ядре 2.6.24 (январь 2008). «2.6.4» на слайде, скорее всего, опечатка. Год (2008) совпадает.

### 6.3. Файловая система OverlayFS
- Позволяет собирать файловую систему **из слоёв**.
- В нужном объёме появилась в ядре **3.18 (2014)**.
- Создаётся через `mount(2)` или `mount(1)`.
- Изменения наследуются **снизу вверх, но не наоборот**.

**Слои:**

| Слой | Роль |
|---|---|
| **Merged** | Итоговое объединённое представление, которое видит контейнер |
| **UpperDir** | Верхний слой, куда пишутся изменения (добавленные, изменённые и удалённые файлы) |
| **LowerDir** (несколько) | Нижние слои, только для чтения: базовый образ и промежуточные слои |

## 7. Как устроен контейнер в Linux

Контейнер = образ файловой системы из слоёв OverlayFS + namespaces + cgroups + chroot.

Что делает среда контейнеризации (например, Docker):
1. Собирает образ из уровней OverlayFS и монтирует его в рабочую директорию контейнера.
2. Создаёт нужные cgroups.
3. Создаёт namespaces.
4. Делает `chroot` в рабочую директорию контейнера.
5. Запускает приложение, указанное в спецификации контейнера.

В образе лежат все библиотеки и программы, нужные для запуска основного компонента, **кроме ядра**.

> Всё это можно повторить руками в обычном shell.

## 8. Преимущества контейнеров

- **Минимальный footprint:** от хост-системы внутри контейнера видно только ядро. Можно запускать любое ПО, совместимое с ядром по ABI.
- **Минимальный overhead:** контейнер потребляет только те ресурсы, которые ему нужны.
- **Быстрый запуск:** миллисекунды (если образы слоёв уже есть).
- **Гибкость обновлений:** образы `lowerDir` можно менять и обновлять независимо.
- **Не нужен админ:** внутри контейнера нечего администрировать.
- **CI/CD:** можно раскатывать прямо в прод (на слайде шутка про «без тестов вообще» — так делать не стоит).
- **Безопасность:** содержимое образов можно сканировать на уязвимости; если сломали контейнер, получают доступ только к ограниченным ресурсам.

## Краткое резюме

1. **VM** дают сильную изоляцию, но дорогие: на каждую своя ОС и ядро, медленный запуск, нужен админ.
2. Контейнеры выросли из **chroot** и **FreeBSD jails**: цель — изолировать приложение и ограничить его в ресурсах, не поднимая целую ОС.
3. В Linux контейнер строится из трёх механик ядра: **namespaces** (изоляция), **cgroups** (лимиты ресурсов), **OverlayFS** (слоистая файловая система).
4. Общий у всех контейнеров только **ядро хоста**, всё остальное в образе.
5. Итог: быстрый запуск, малые накладные расходы, воспроизводимое окружение, независимое обновление слоёв.
