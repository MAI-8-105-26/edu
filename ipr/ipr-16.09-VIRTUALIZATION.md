# Виртуализация
### можно, а зачем?
- за исключением жестких нагрузок железо стоит
- хочется движухи))
	- загрузить железо!
	- а потом продавать его школьникам под сервера майнкрафт!!
	- запустить другую операционную систему на существующей
	- сделать так, чтобы ос можно было запускать независимо от конфигурации железа (миграция и переносимость)
	- заизолировать эту ос от внешнего мира
	- сделать так, чтобы можно было контролировать эту ос извне
	- сделать так, чтобы всем этим можно было управлять при помощи API
	- *и много чего еще*

### основные проблемы
- любая современная ОС ожидает полный контроль над железом.
- железа у нас немного, а именно:
	- процессов (иногда их бывает несколько)
	- оперативка
	- разные устройства (KVM, диски, сеть)
	- шото *странное* (Intel ME, ACPI, USB, ...)
- ос ожидает, что все это реально и все это работает
- для всего этого у ОС есть куча драйверов
- у всего етого есть *баги*, причем некоторые из них общеизвестны (лол)
- а некоторые не очень
- нужно сделать так, чтобы ос ничего не зародозрила

### первый подход к снаряду
классическая архитектура фон Неймана
потом тут картинка

- процессор читает инструкции и операнды из ОЗУ
- выполняет операции и пишет результаты обратно (или нет)
- а давайте это все реализуем программно!
- возьмем *(где?)* документацию на процессор
- напишем программу на надежном языке C (ок, ок, на Rust)
- будем читать ею инструкции и операнды и выполнять их
- мы молодцы!
- вознкает вопрос - что делать с вводом/выводом?
- не беда, возьмем документацию на устройства...
- такого рода подход называется **программной эмуляцией**
- имеет полное право на существование на несовместимых архитектурах (железо CISC, эмулируем RISC и наоборот)

- современный процессор является *почти* фон Неймановским
- у него ***внезапно*** есть кэш(и):
![[Pasted image 20260917104401.png]]
- эти кэши раздельные для инструкицй и данных
- для инструкций процессоры применяют pipelining:
![[Pasted image 20260917104450.png]]
- внутри pipelines существует огромное количество оптимизаций:
	- предсказание ветвлений (то есть процессор собирает некую статистику что он делает по веткам инструкций if/else и прикидывает что будет дальше. упрощает себе работу)
	- спекулятивное выполнение
	- выполнение по мере готовности
	- и много чего еще
- во все это вложены миллиарды ~~долларов~~ рублей
- из-за всего этого мы страдаем от Spectre/Meltdown
- концепция эмуляции перечеркивает все эти достижения
- нужно делать что-то другое...

### первые итоги
- у нас есть Гипервизор, который сидит в кольце 0
- Гипервизор полностью контролирует ОС, находящиеся в кольце 1
- Сама ОС об этом мало что знает и ей хорошо
- Приложения по-прежнему работают в кольце 3
- ОС видит виртуальную память, данную ей гипервизором
- ОС видит виртуальные устройства, данные ей гипервизором
- Код (инструкции процессора) ОС выполняются на реальном CPU
- Виртуальные устройства эмулируются программно
- На выходе получаем Type 1 Hypervisor
- Классические примеры: VMware ESXi, Linux KVM, M$ Hyper-V
- Однако имеются некоторые сложности..


### Виртуализация: Type 1 Hypervisors
Классическая иллюстрация для собеседований:
![[Pasted image 20260917150333.png]]

Для начала, картина реального мира несколько сложнее:
![[Pasted image 20260917150423.png]]

- ОС ожидает видеть себя в 0 кольце
- Внутри VM может быть запущена другая VM
- Некоторые устройства нельзя разделять (GPU, RDMA)
- Их нужно целиком отдавать в конкретную VM
- Для всего этого нужна поддержка со стороны процессора:
	- Intel VT-x, AMD SVM (AMD-V)
	- Intel VT-d, AMD Vi
	• PCI SIG Single Root I/O Virtualization - SR-IOV
- Поддержка этой красоты разнится в зависимости от платформы
- Необходимые извинения за предельное упрощение )

#### Итоги гипервизоров 1 типа
- Минимально возможный overhead по производительности
- Максимально возможная изоляция VM
- Максимальный контроль ресурсов хоста
- Сложная и не всегда понятная система управления
- Используются в облаках, дата-центрах и ресурсоемких задачах
- Умеют в enterprise технологии (HA, горячая/холодная миграция..)
- Стоимость лицензий варьируется от 0 (KVM) до ∞ (vSphere Enterprise Plus)


### Виртуализация: второй подход
- Давайте возьмем обычную ОС (Windows 11)
- Будем запускать VM как процесс внутри ОС
- Всякие нехорошие инструкции будем программно эмулировать
- Все (совсем все) функции ввода-вывода поставляет ОС
- В итоге получаем Type 2 Hypervisor
- Классические примеры: VMware Workstation (Fusion), Oracle VirtualBox, Parallels Desktop
- Некоторая дискуссия

#### Type 2 Hypervisors
![[Pasted image 20260917150700.png]]

- Значительный overhead по производительности
- Сниженная изоляция за счет доступа к ОС хоста
- Ресурсы хоста делятся между VM и приложениями ОС (dota 2)
- Управление через обычное приложение на ОС хоста
- Используются в разработке, тестировании и обучении
- Продвинутая функциональность отсутствует как класс
- Дешево и сердито


## Фичи и достоинства виртуальных машин
- Независимость от железа хоста (есть исключения)
- Переносимость – скопировал и унес
- Масштабируемость (процессор, память, диск) в т.ч. на горячую
- Изоляция и безопасность
- Возможность сохранения состояния (snapshots)
- Быстрое развертывание и шаблонизация (ovf/ova)
- Развертывание множества VM из одного шаблона (VPS, VDI)
- Удобство создания бэкапов
- Возможность oversubscription (VPS за 90 рублей)
- Управление развертыванием с помощью API (IaaC, PaaS, …)
- Всякие странные штуки (memory ballooning, UKSM, …), недостижимые на реальном железе
